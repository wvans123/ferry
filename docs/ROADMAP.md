# Ferry 路线图（2026-11 起）

原则：
- **按模块加功能**：每次只动一个模块，只测这个模块，发版前再跑全套自测。
- **电脑这边越薄越好**：电脑只负责"动手"（读写文件、跑命令），对话、记忆、任务状态尽量放在服务端。这样换一个外壳（IDE、DSH、Codex、Claude Code）也不丢东西。

## 现在的分工

| | 电脑（ferry 客户端） | 服务端 |
|---|---|---|
| 已经在这边 | 工具执行、权限、记忆文件、待办、/goal、后台任务、子 agent 调度 | 对话全文、模型和 Key、脱敏、限流/冷却/回退、写摘要、用量 |
| 计划搬到服务端 | 记忆、待办、/goal 状态、后台任务的状态（电脑只留执行） | — |

## 接到别的工具里：三层，从省事到费事

### A. `ferry relay`：本机一个接口，谁都能接（先做）
在工作电脑上开一个只给本机用的接口（`http://127.0.0.1:端口`），同时会说 OpenAI Chat、OpenAI Responses、Anthropic Messages 三种格式。别的工具把它当成普通的模型地址，ferry 负责：
- 只上传新增内容，单个请求不超过 1 MB；
- 服务端已有的消息只发引用；
- 公司网关确认、证书、限流时改问回退模型这些，和 ferry 自己一样。

能直接接上的：

| 工具 | 怎么接 |
|---|---|
| DSH | llm-pi-ai 的 providers 里 baseURL 填这个地址 |
| Codex | config.toml 里自定义 model_provider，base_url 填这个地址 |
| Claude Code | `ANTHROPIC_BASE_URL` 填这个地址 |
| VS Code 里的 Cline / Continue / Roo | 选"OpenAI 兼容"，填这个地址 |
| Cursor | 接不了：Cursor 的请求从它自己的服务器发出，到不了你电脑上的本机接口 |

这一层里，agent 和工具都是那个工具自己的；Ferry 提供的是"通道 + 模型 + Key + 脱敏 + 限流"。

### B. DSH 插件（重点，开源）
DSH 底层也用 pi-ai，所以可以把 Ferry 的传输方式注册成 DSH 的一种模型接口，比 A 更完整：
- 模型列表来自 Ferry 服务端；
- 冷却改用回退、服务端写摘要、上下文上限自动学习；
- 可选：把 Ferry 的工具（Office、团队看板、记忆）也做成 DSH 插件。

开始前先读 DSH 的插件接口源码，确认注册模型接口的写法。

### C. IDE 插件（往后放）
VS Code 插件：一个聊天面板，后面跑 `ferry`（pi 有 RPC 模式）。很多需求用 A + Cline/Continue 就能满足，所以排在最后。

## agent 和团队

参考 DeepSeek 的 Super-agent 文章：

1. **负责人做"分派"，不做"执行"**：Lead 不给 bash、用便宜快的模型，只拆任务、派活、汇总。文章的实验里，只靠提示词，模型 5 次里 0 次主动分派；所以分派要靠结构，不靠提示词。
2. **看门狗**：定时检查每个成员有没有实际进展、是不是在原地打转，卡住了就在任务里留言或叫醒负责人。
3. **长内容只放 ID 和摘要**：任务、评论、工具输出进上下文时只放开头和 ID，要看全文再读。
4. **状态搬到服务端**（见上表）：成员换电脑、电脑睡眠后醒来，都能接着做。

## 顺序

| 顺序 | 模块 | 为什么 |
|---|---|---|
| 1 | A. `ferry relay` | 一个模块，马上让 DSH、Codex、Claude Code 都能用上 Ferry 的通道 |
| 2 | B. DSH 插件 | 开源、你最看重；在 A 的基础上补全 |
| 3 | 团队：轻量 Lead + 看门狗 | 让团队真正省心 |
| 4 | 状态搬到服务端 | 为插件化打底 |
| 5 | C. IDE 插件 | 需求还在时再做 |

暂不做：邮件、聊天软件作为事件来源。
