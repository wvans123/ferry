# Ferry 设计说明

## 1. 目标与约束

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| 工作电脑对外的单个请求体 ≤ 1MB | 公司网络规定 | 不能每轮重发完整对话；大内容要拆块 |
| 工作电脑不放模型 API Key | 安全 | 模型调用只能在服务端 |
| 工作电脑只能经公司代理上网 | 网络环境 | 客户端所有请求统一走代理 |
| 两端都是 Windows | 使用环境 | 不依赖 Docker；Python 和 Node 直接运行 |

## 2. 分工

客户端是对话的唯一可信来源：记录、文件、工具执行都在客户端。服务端可以随时丢掉它的缓存，代价只是一次全量重传。

| 能力 | 客户端 | 服务端 |
|---|---|---|
| 对话记录 | 完整保存（pi 的会话文件） | 缓存，默认保留 7 天 |
| 读写文件、执行命令 | ✓ | |
| 禁止目录、执行确认 | ✓（服务端无法绕过） | |
| 组装最终提示词、服务端规则 | | ✓ |
| 模型选择、参数适配、API Key | | ✓ |
| 访问日志、审计日志 | | ✓ |

## 3. 一次任务是怎么循环的

agent 不是"发一条、收一条"就结束。一个任务要来回很多轮，每一轮是一次完整的"工作电脑 → 服务端 → 模型 → 服务端 → 工作电脑"。

**谁决定继续还是结束：** 模型。模型的回复里如果有工具调用（读文件、改文件、执行命令），工作电脑上的 pi 就执行它，把结果作为一条新消息，再发起下一轮；如果回复里只有文字，这个任务就结束了。

**谁在推动循环：** 工作电脑上的 pi。服务端不知道"任务"的存在，它只处理一次次独立的请求。它缓存的会话只是为了省流量，丢了也能恢复。

**每一轮的两个请求：**

1. `commit`：只上传这一轮新增的消息（上一轮模型的指令 + 本地执行的结果）；
2. `chat/completions`：只带会话引用，几百字节。服务端拼回完整上下文发给模型，再把回复流式返回。

下面是一次真实运行的记录（假模型，任务是"把 Project Titan/notes.txt 里的工单号改成 EMP-99999"）：

| 轮次 | 工作电脑上发生了什么 | 上传新增消息 | 模型请求 | 服务端发给模型 | 模型这一轮的回复 |
|---|---|---|---|---|---|
| 1 | 你输入任务 | 6,160 字节：系统提示、你的话、4 个工具的定义 | 375 字节 | 6,463 字节，2 条消息 | 调用 `read` 读 notes.txt |
| 2 | pi 读文件，结果作为新消息 | 384 字节：模型的读文件指令 + 文件内容 | 375 字节 | 6,809 字节，4 条消息 | 调用 `edit` 改工单号 |
| 3 | 弹窗确认后改文件，结果作为新消息 | 463 字节：改文件指令 + 修改结果 | 375 字节 | 7,217 字节，6 条消息 | 只有文字"已改好"，循环结束 |

可以看到：

- 模型每一轮收到的都是完整上下文，而且一轮比一轮大；
- 工作电脑每一轮只上传新增的几百字节，加一个几百字节的引用；
- 第 1 轮上传最大，因为要带上系统提示和工具定义。之后的每一轮只多出"模型指令 + 执行结果"。

真实任务往往要几十轮。上下文接近模型上限时，pi 会先把较早的历史压缩成摘要，再继续循环（自测 F5）。

**和 Cursor 的区别：** Cursor 在一个请求里由服务端连续下发多个工具调用，客户端在同一条连接上逐个回传结果，循环由服务端推动。Ferry 由客户端推动，每一轮是一次新请求。两种做法的效果一样；Ferry 的做法更简单，也更容易穿过公司代理（不需要长时间保持双向连接），代价是每一轮多一个几百字节的请求。

## 4. 增量同步协议

pi 每轮请求都带完整的 `messages`。Ferry 的模型接入点在请求发出前把它换成"会话引用"。

1. 每条消息序列化成 JSON 字符串 `m_i`，计算哈希链：`h_0 = ""`，`h_i = sha256(h_{i-1} + m_i)`。
2. 会话 ID：`conv = sha256(进程随机盐 + m_0 + m_1)`。加盐是为了避免两个开头相同的会话在服务端互相覆盖。
3. 客户端记得服务端已确认的 `(count, hash)`。如果当前消息的前 `count` 条哈希仍等于 `hash`，只上传 `m_count …` 之后的部分，否则从 0 开始。
4. 上传内容 `{"append": [...], "tools": 工具定义或 null}`：
   - 不超过 `chunkBytes`（默认 512KB）直接 `POST /v1/ferry/commit`；
   - 超过就按字节切块，逐块 `POST /v1/ferry/upload/{id}/{seq}`，最后 `commit?upload=id&parts=n`。每个请求体都不超过当前的块大小，图片的 base64 和文字一样算；
   - 请求被半路挡下（网关 403、Cloudflare 5xx、连接断开）时等一下再发，最多三次；403 时把块大小减半，本次运行后面的块都用小的。服务端按序号存块，后发的小块直接顶替序号，所以服务端不用改（`client/lib/upload.mjs`）。
   - `blocked.log` 每条记的是实际发出的那个请求的大小（`sent`），`part` 是第几块，`total` 是整次上传的大小，`images` 是这次上传里图片的张数和字节数。
5. 服务端校验 `base` 和 `base_hash` 与自己记录的一致，追加并返回新的 `(count, hash)`。不一致返回 409，客户端立即改为全量上传。
6. 真正的模型请求只带 `{"ferry": {conv, count, hash, tools_hash}}`。服务端取出缓存，拼回完整请求。

工具定义按内容哈希单独缓存，同一个进程只上传一次。

**调用模型前一刻缓存丢失：** 服务端如果在第 5 步和第 6 步之间丢了缓存，模型请求会得到 409。pi 本身不重试 409，所以 Ferry 的接入点自己处理：只要还没有任何输出，就清空本地记录的服务端状态并重试一次，这一次会全量上传（自测 F17）。

**为什么用哈希链而不是 Cursor 的 Merkle 树：** Cursor 的 Merkle 树用于代码库文件同步，文件可以任意改动；对话是只追加的序列，哈希链足够，而且实现简单。客户端压缩上下文或回到之前的分支时，前缀对不上，自然退化为全量上传。

## 5. 服务端组装提示词

- `rules/_global.md` 对所有人生效，`rules/<项目名>.md` 在客户端从同名目录启动时生效。项目名默认是工作目录的文件夹名，可用 `FERRY_PROJECT` 覆盖。
- 规则以 `<server-rules>` 段追加到系统提示末尾，不替换 pi 自带的工具说明，因此不会和真实工具对不上。
- 每次请求都重新读规则文件，修改后下一轮生效。

## 6. 脱敏（0.26 删掉）

0.25 以前有过可逆脱敏：词表和正则命中的内容换成 `[FERRY-XXXXXXXX]` 占位符再发给模型，回复里再换回来。它默认关闭，对 Claude 原生接口不起作用，作者也没在用，0.26 删掉了。问题报告（`/report`）发到 GitHub 前另有一份简单的过滤，见代码地图。

## 7. 模型适配

不同提供商对参数的支持不一样。每个模型可以配置：

- `drop_params`：去掉的参数；
- `rename_params`：改名的参数，例如 `max_completion_tokens → max_tokens`；
- `extra_params`：附加的参数；
- 另外按 `max_tokens` 封顶。

## 8. 嵌入 pi 而不 fork

客户端直接调用 pi 公开的 `main(args, { extensionFactories })`，传入三个内联扩展：

- `ferry-sync`：注册名为 `ferry` 的模型提供方。它复用 pi 自带的 OpenAI 兼容流式实现，只接管 `onPayload` 做增量同步。上下文压缩等内部请求也走同一条路。
- `ferry-guard`：在 `tool_call` 事件里执行禁止目录和执行确认。
- `ferry-brand`：替换终端头部。

pi 的配置目录指向 `~/.ferry/agent`，和用户自己装的 pi 互不影响。所有 pi 子包锁定同一版本（`overrides`），避免版本错位。

## 9. 多用户与版本

- 会话缓存和上传分块都按用户隔离，一个用户读不到另一个用户的会话缓存（自测 F18）。
- 令牌比较用恒定时间算法；密钥和令牌少于 16 个字符时服务端拒绝启动（F20）。
- 客户端每个请求都带 `x-ferry-protocol`，主版本不同时服务端返回 426，`ferry doctor` 会直接提示升级哪一边（F19）。

## 10. 日志

- `access.jsonl`：用户、路径、请求体大小、状态码。
- `audit.jsonl`：模型调用（用户、项目、模型、消息数、发给模型的字节数、用量、耗时），以及每次同步的提交记录。

两种日志都不含对话内容，自测 F11 会检查这一点。

## 11. 压缩：客户端和服务端各管一层

| 层 | 谁做 | 什么时候 | 做什么 | 会不会丢信息 |
|---|---|---|---|---|
| 摘要压缩 | 客户端（pi） | 上下文接近模型窗口（DeepSeek 128K tokens） | 让模型把较早的历史写成摘要，之后用摘要代替原文 | 会，换来更长的会话 |
| 请求封顶 | 服务端 | 拼好后发给模型的请求超过上限（默认 900KB，`max_upstream_bytes`） | 从最旧的工具输出开始，换成一句"这段旧输出已删除，需要可重新执行工具"，直到不超过上限 | 只影响这一次发给模型的内容，客户端的记录不变 |

为什么服务端也要一层：模型窗口按 token 算，网络限制按字节算，两者对不上。中文、代码、JSON 的 token 和字节比例差别很大，pi 的摘要压缩可能还没触发，请求就已经超过 1MB 了。服务端封顶保证"发给模型的请求不超过上限"一定成立（自测 F21）；而服务端和模型之间不受公司网络限制时，可以把上限设为 0 关掉。

封顶不碰系统提示、用户自己说的话和最近 6 条消息，所以当前这一步要用的内容总在。如果删光旧输出仍超过上限，服务端返回 413，提示执行 `/compact` 或新开会话。

## 12. 本机模式、安装和更新

**本机模式**：没有执行过 `ferry login` 时，每个 `ferry` 进程在后台启动一个只属于自己的服务端（随机端口、随机令牌、只监听 127.0.0.1），进程退出时一起关掉。服务端用零配置启动：模型是 DeepSeek，Key 读环境变量 `DEEPSEEK_API_KEY`，规则和词表自动生成在 `~/.ferry-server`。所以第一次使用只需要 `ferry` 一条命令（自测 F22、F23）。

每个窗口各起一个服务端，而不是共用一个后台常驻进程，是为了：关掉一个窗口不会影响另一个窗口；升级后不会有旧版本的服务端还在跑；环境变量（Key、代理）改了，重开窗口就生效。代价是每次启动多 1 到 2 秒。

**安装**：GitHub 发布页上的 `ferry-windows-x.y.z.zip` 带有客户端全部 Node 依赖和服务端全部 wheel（Windows x64，Python 3.11 到 3.14），`ferry install` 不需要联网：

1. 把程序复制到 `%LOCALAPPDATA%\Ferry\versions\<版本>`；
2. 用 pip 把服务端装进电脑上已有的 Python（不建虚拟环境）；
3. 在 PATH 上的目录（Node.js 的全局命令目录）里放一个 `ferry.cmd`，它通过 `launcher.mjs` 运行 `current.txt` 指向的版本。

**更新**：`ferry update` 查询 GitHub 的 latest release，有新版本就下载 zip，解压后运行新版本自己的 `install`，最后改 `current.txt`。正在运行的旧版本不受影响，保留上一个版本用于回退（自测 F24）。访问不了 GitHub 时，`ferry update <zip>` 用手动下载的文件。

**发布**：main 分支上的版本号还没有对应的 release 时，测试通过后 GitHub Actions 构建安装包并创建 release（发版就是改版本号）；每次提交在 Linux 和 Windows 上跑单元测试和端到端自测。

## 13. 服务端放在哪、接哪家模型

服务端有三种放法，客户端都不用改，只差一次 `ferry login`：

| 放法 | 适合 | 工作电脑发出的流量 | Key 在哪 |
|---|---|---|---|
| 本机模式（默认） | 试用；模型服务商允许从这台电脑直接访问 | 直接到模型 API | 这台电脑的环境变量 |
| 自己的电脑 | 有能让工作电脑访问到的中转（工作电脑连不上他的电脑） | 到中转 | 自己的电脑 |
| 云服务器 | 正式使用；要用 Claude / OpenAI 时必须选它们支持的地区 | 只到 Ferry 服务端（HTTPS，≤ 1MB/次） | 云服务器 |

模型接入统一用 OpenAI 兼容的 `/chat/completions`：

- DeepSeek、OpenAI 本来就是这个格式；
- Claude 用 Anthropic 官方的 OpenAI 兼容接口（`https://api.anthropic.com/v1/`）。它支持流式和工具调用，但官方说明它主要用于测试和对比，生产建议用原生接口，而且不支持提示词缓存。agent 每轮都重发整个上下文，提示词缓存能省下大部分输入费用，所以"Claude 原生接口"排在路线图第一位。

零配置时，模型清单在服务端数据目录的 `models.toml` 里：第一次启动时按环境里有哪些 Key 生成（有 Key 的启用，其余写成注释），之后每次请求前检查文件是否改过，改过就重新读取，所以改模型不用重启；文件写错时保留上一份能用的清单，并在日志里提示。

**模型由服务端决定。** 客户端只看到一个叫 `auto` 的模型，请求里也只写 `auto`。服务端按 `[routing]` 设置挑真正的模型：

- `default`：干活（agent 每一轮）用的模型；
- `summary`：写上下文摘要用的模型。客户端在同步时标明请求用途（pi 的摘要请求有固定的系统提示开头），服务端据此分流；这时 `auto` 报给客户端的上下文窗口取两个模型里较小的那个，保证摘要请求放得下；
- `expose`：为 true 时客户端也能用 `/model` 选具体模型。

这样换模型、换服务商、给摘要换便宜模型，都只改服务端，工作电脑上什么都不用动（自测 F25）。

**服务端存不存对话**（`session_store`）：

| 值 | 服务端保存什么 | 每轮上传 | 适合 |
|---|---|---|---|
| `disk`（配置文件默认） | 会话缓存写进 SQLite，保留 `session_ttl_days` 天 | 只传新增部分 | 远程服务端，省流量，重启后不用重传 |
| `memory`（零配置默认） | 只在内存，重启就没了 | 只传新增部分 | 本机模式（对话本来就在这台电脑的会话文件里），或不想落盘 |
| `none` | 每次模型调用结束就删 | 每轮整段重传，按 512KB 分块，单个请求仍不超过 1MB | 服务端完全不留对话；代价是流量大 |

无论哪种，完整对话始终保存在客户端（自测 F26）。Claude 和 OpenAI 的上下文窗口按 20 万 token 报给客户端（模型本身更大）：这样 pi 会在请求接近 1MB 之前先做摘要，每轮的费用也更低。

`ferry doctor` 最后一步通过 `POST /v1/ferry/check` 让服务端给每个模型发一个"回答 OK"的小请求，并把常见失败翻译成下一步该做什么：401 是 Key 错，402 是余额不足，403 多半是地区不受支持，连接错误是网络或代理。

上下文管理和记忆的方案（参考 pi、Cursor、Claude Code、Codex 的做法）见 [CONTEXT-AND-MEMORY.md](CONTEXT-AND-MEMORY.md)。

## 14. 服务端管理页

`/admin` 是给运行服务端的人用的本机网页（`server/ferry_server/admin.html`，单文件，不依赖外网资源）。安全上有三道门：

1. 只接受来自 127.0.0.1 / ::1、且不带任何代理或 Cloudflare 请求头（`cf-connecting-ip`、`x-forwarded-for` 等）的请求。隧道进来的请求也来自本机，但一定带这些头；
2. 要有管理钥匙：钥匙存在服务端数据目录的 `admin-key` 里，`ferry-server --ui` 打开的链接带着它，换成 SameSite=Strict 的 cookie；
3. 修改类请求还要带 `X-Ferry-Admin` 头，别的网站的页面发不出这种请求（会触发跨域预检）。

能在页面上改的设置（外网地址、会话保存方式、请求上限、详细记录）写进数据目录的 `server.toml`，立即生效；环境变量仍然优先。会话保存方式切换时换掉会话库，正在进行的对话下一轮整段重传一次。

模型配置以**服务商**为核心（`models.toml` 里的 `[providers.*]`，模型用 `provider = "..."` 引用）：预设带好地址和推荐模型，页面上只需要填 API Key；Key 存在 `secrets.toml`，接口只返回末 4 位。旧写法（模型自带地址和 `api_key_env`）仍然可用，页面上按地址自动归到对应服务商下，保存时转换成新写法。页面的结构和参考来源见 [ADMIN-DESIGN.md](ADMIN-DESIGN.md)。

## 15. 客户端 agent 的扩展（v0.10）

全部写成 pi 的扩展，在 `ferry.mjs` 里通过 `extensionFactories` 装进去，不改 pi：

| 扩展 | 做什么 | 用到的 pi 接口 |
|---|---|---|
| `memory.mjs` | 两层记忆（user / project），每层一个 `MEMORY.md` 索引加每条一个文件；索引作为系统提示里的 `<ferry_memory>` 段，每轮开始时重读；`memory` 工具只能碰记忆目录，所以不需要审批 | `before_agent_start` 改 `systemPromptOptions.sections`，`registerTool`，`registerCommand` |
| `subagent.mjs` | `task` 工具：用 `createAgentSession` 在同一进程里另起一个会话（`SessionManager.inMemory`），只装 Ferry 自己的扩展；同步时 `purpose = "subagent"`，服务端调用记录能区分；审批借用主会话的 `ctx.ui`，标题里写明是哪个子 agent | SDK、`tool_execution_start` 事件、`onUpdate` |
| `tools.mjs` | `todo`（状态放在工具结果的 `details` 里，切分支时从会话重建）；长输出写文件（`tool_result` 事件里替换结果，pi 已经截断的命令输出从它的完整临时文件取全文）；`history_search`（在当前分支的全部消息里搜，包括被摘要替换掉的） | `tool_result`，`sessionManager.getBranch()`，`ui.setWidget` |
| `toolbins.mjs` | pi 用离线模式启动，不会自己下载 fd 和 rg：安装包带 `vendor/<平台>/`，`ferry install` 和每次启动时拷到 `agent/bin`；git 仓库安装时从 GitHub 下载固定版本 | pi 的 `getBinDir()` 约定 |

系统提示变化（记忆更新、工具变化）由 pi 以增量的方式记进对话，第一条系统消息不变，所以 Ferry 的增量同步不受影响。

跟着 pi 更新：Ferry 不 fork pi，只依赖它公开的接口（`main()` 的 `extensionFactories`、扩展事件、SDK）。`update-pi.yml` 每周把依赖换成 pi 最新版，跑全部测试（含伪终端里的界面冒烟测试 F38），通过才发布。接口如果有不兼容的改动，测试会失败，发布就不会发生。

## 代码地图

每个问题是怎么解决的、代码在哪。

| 问题 | 做法 | 代码位置 |
|---|---|---|
| 单个请求 ≤ 1MB，但长会话的上下文会超过 1MB | 客户端每轮只上传新增消息，用哈希链校验双方一致；超过 512KB 的内容拆块上传；服务端拼回完整上下文再发给模型 | `client/lib/sync.mjs`、`server/ferry_server/store.py` |
| 服务端缓存丢了怎么办 | 客户端始终保存完整记录；服务端只是缓存。校验不一致时返回 409，客户端自动全量重传 | 同上 |
| 提示词由谁决定 | 和 Cursor 一样由服务端完成最终组装：通用规则 + 按项目的规则，改完下一轮即生效，不用动客户端 | `server/ferry_server/prompt.py` |
| 用哪个模型由服务端决定 | 客户端只看到一个 `auto` 模型；服务端按设置把干活的请求和写摘要的请求分别发给不同模型。每家服务商的模型在工作电脑上各自列出（`kiro/模型名`）；勾了合成一组的几家，同名模型在它们之间分配和切换（`pool.py`）；接口有 OpenAI 兼容、Anthropic Messages、OpenAI Responses 三种 | `server/ferry_server/app.py`、`config.py`、`pool.py`、`responses.py` |
| 服务端存不存对话 | 设置项 `session_store`：存磁盘（省流量）、只存内存、完全不存（每轮整段重传，仍按 512KB 分块，单个请求不超过 1MB） | `server/ferry_server/store.py` |
| 本地安全底线 | 禁止目录、执行前确认都在客户端执行，服务端无法绕过；拦截原因里不含受保护的名字 | `client/lib/guard.mjs` |
| 可审计 | 访问日志和审计日志只记大小、模型、用量，不记对话内容 | `server/ferry_server/app.py` |
| 上下文太长 | 长输出在客户端写文件，只给模型开头结尾；旧的长工具输出超过 `trimOldOutputs` 后换成一行说明；到 `compactAt` 时写摘要（由服务端写，失败会换模型、分段），压缩后能用 `history_search` 找回原文；服务端可以给发给模型的请求设上限（默认不设），超了从最旧的工具输出开始删 | `client/lib/tools.mjs`、`server/ferry_server/fit.py`、`prompt.py` |
| 记忆放哪 | 客户端：内容本来就是关于这台电脑上的代码和你的习惯；服务端只转发，换服务端不丢记忆。只有目录进系统提示，正文按需读取 | `client/lib/memory.mjs` |
| 子 agent | 在同一个进程里另起一个 pi 会话（内存里，不存盘），作为一个独立对话同步到服务端；审批对话框借用主窗口 | `client/lib/subagent.mjs` |
| 权限 | 每次工具调用先过 `decide()`：受保护路径 → 禁止规则 → 模式 → 危险命令 → 询问规则 → 只读命令 → 允许规则；复合命令按 `&&` `;` `|` 拆开逐段判断。几个工具同时要确认时排队一个一个问，前一个回答存下的规则后面的直接用 | `client/lib/permissions.mjs`、`guard.mjs` |
| 系统提示 | 用 Ferry 自己的开场和工作方式代替 pi 的（不再提 pi 文档，避免模型去翻 agent 自己的配置），保留 pi 的工具说明，加上操作系统、shell、日期、是否 git 仓库 | `client/lib/prompt.mjs` |
| 联网 | 在客户端执行，走公司代理，识别网关的确认页（按地址和页面文字）并报告，不点击通过；`blockedSites` 里的网站不打开 | `client/lib/web.mjs` |
| 搜索和读网页 | 照 Claude Code 的做法，搜索和公开网页都由服务端去做（它是模型的客户端）：搜索默认用 DeepSeek 的搜索 API（服务端有 DeepSeek Key 时），也可以用模型自带的搜索或别的搜索 API；读网页用 DeepSeek 的读网页 API 或服务端自己下载，带问题时由摘要模型读，只交回回答。工作电脑只发搜索词和地址，Key 都在服务端。内网和私有地址、`localSites`、服务端读不到的网页、PDF 和 Office 文件，在工作电脑上读（走公司代理和网关），要登录或操作的用浏览器。服务端拒读私有网络地址（含跳转），工作电脑也不把这类地址发上去。怎么查资料写在系统提示里，大问题交给内置的 research 子 agent | `server/ferry_server/search.py`、`client/lib/web.mjs`、`prompt.mjs`、`subagent.mjs` |
| 公司网关要先确认 | 启动时发现服务端地址被网关转到确认页，就用浏览器打开那一页，每 2.5 秒检查一次，你确认后自动继续；会话中途确认过期，打开确认页、等确认后自动重发（最多等 3 分钟）；`ferry check` 手动查 | `client/lib/gateway.mjs` |
| 跟着 pi 更新 | Ferry 只用 pi 公开的扩展接口，不改 pi 本身，所以不 fork。每周一自动检查 pi 新版本：换上新版本后在 Linux 和 Windows 上跑全部测试（含终端界面冒烟测试），都通过才提交并发布 Ferry 新版本 | `.github/workflows/update-pi.yml`、`scripts/bump_pi.mjs` |
| 斜杠命令和自定义 | pi 自带命令里用不上的，启动时从它的命令表里拿掉（只是不列出）；用户和项目的命令、技能目录通过 pi 的 `resources_discover` 事件加进去，同名时项目覆盖用户 | `client/lib/trim.mjs`、`client/lib/commands.mjs` |
| 浏览器 | agent-browser（Rust 写的命令行程序，用 CDP 控制浏览器）放进 pi 的 bin 文件夹，agent 用 bash 调用；Ferry 设好用哪个浏览器、自己的资料夹、要不要窗口，技能说明只在浏览器打开时列出；看页面的子命令算只读；ferry 退出时关掉浏览器 | `client/lib/browser.mjs`、`client/browser-skill/` |
| 问题报告 | 工作电脑只能连服务端：`/report` 让对话里的 agent 写报告（它最清楚出了什么事），用户在终端看过全文再发；只自动附上版本和工具次数。服务端隐去管理页上列的词、内网 IP、邮箱、手机号、Key、路径里的用户名，存一份，再用自己的 GitHub 令牌开 issue | `client/lib/report.mjs`、`server/ferry_server/report.py` |
| 撤销 | 每次请求里第一次 edit/write 一个文件前，把原内容按哈希存一份；`/rewind` 选一个请求，把它和之后改过的文件恢复，并告诉模型这些文件变了 | `client/lib/checkpoint.mjs` |
| 钩子 | `afterEdit` 在工具结果出来后运行，失败输出追加到工具结果里交给模型；项目的钩子文件按内容哈希征得同意，改了要重新同意 | `client/lib/hooks.mjs` |
| /goal | 目标存成会话里的一条记录（恢复对话时还在）；agent 每次要停下时（pi 的 `agent_before_settle`），如果目标还在进行，就补一条"对照目标继续"的消息并要求再跑一轮；agent 用 `goal_update` 先记下完成标准（criteria），最后报告完成（每条标准给证据，缺了就退回，最多两次）或卡住；进行中用户说的话记进目标（最近 10 条）；标准和这些记录放在每条继续消息和压缩后的隐藏消息里，不放进系统提示，免得每次改动都换掉同步的第一条消息；token 预算和轮数上限到了就要求它写进度报告 | `client/lib/goal.mjs` |
| 后台任务 | 后台命令的输出写到文件，`job_output` 读末尾；后台子 agent 是不等结果的子会话；结束时提示你，并在你下一条消息里告诉 agent | `client/lib/jobs.mjs` |
| Claude 原生接口 | 客户端按服务端说的接口类型，用 pi 自带的 Anthropic 提供方（思考、图片、缓存标记都由它处理）；同步前把每轮都会移动的缓存标记取下、服务端再放回，所以照样只传新增部分；服务端把请求转给 Anthropic，并从事件流里记下用量 | `client/lib/sync.mjs`、`server/ferry_server/app.py` |
| 费用 | 价格写在服务端的模型配置里（预设已填好 Claude 和 GPT），随模型列表下发给客户端，pi 自己累计；服务端按每次调用的用量另算一份，管理页汇总 | `server/ferry_server/usage.py` |
| 公司代理和证书 | 客户端所有请求统一走代理（环境变量或配置项），支持 NO_PROXY；同时信任系统证书和 `caFile`，并写成 `ca-bundle.pem` 交给 agent 执行的命令（curl、git、Python、Node） | `client/lib/config.mjs` |
| 好装、好更新 | 离线安装包 + `ferry install`；`ferry update` 从 GitHub 发布页取最新版。每次发版有三个文件：完整包、只含 Ferry 自己代码的小包（几百 KB）、依赖指纹 `ferry-deps-*.json`（node_modules、服务端依赖、fd/rg 各一个哈希）。指纹和已装版本的 `deps.json` 一样时只下小包，依赖用硬链接从已装版本接过来（不占额外空间），否则下完整包。服务端装在每个装过它的 Python 里，正在跑的旧版自动换成新版；没登录远程服务端时自动在本机启动服务端 | `client/lib/setup.mjs`、`scripts/build_bundle.py` |
| 不重复造轮子 | Agent 循环、工具和终端界面直接用开源的 [pi](https://github.com/earendil-works/pi)（MIT），通过它公开的 `main()` 和扩展接口嵌入，不 fork 内核 | `client/bin/ferry.mjs` |


### 和 Cursor 的对应关系

| | Cursor | Ferry |
|---|---|---|
| 对话记录 | 存在客户端，每次请求带上 | 存在客户端；服务端额外缓存一份，所以每次只需传新增部分 |
| 工具执行（读写文件、命令） | 客户端 | 客户端 |
| 最终提示词组装 | 服务端（官方文档说明即使用自己的 API Key 也经服务端） | 服务端 |
| 模型调用和 API Key | 服务端 | 服务端 |
| 代码库语义检索 | 服务端索引 | 不做（要把代码上传建索引）；用 grep + 子 agent 搜索 |
| 记忆 | Memories（服务端生成，需批准） | 客户端文件，模型用 `memory` 工具读写，你可以直接改 |
| 子 agent | 有 | `task` 工具，内置 explore / general，可自定义 |
| 权限 | 有 | 四种模式、按项目记住的规则、只读命令白名单、危险命令总是问（参考 Claude Code） |
| 读网页、搜索 | 服务端执行 | 在工作电脑上执行（受公司网关管） |
